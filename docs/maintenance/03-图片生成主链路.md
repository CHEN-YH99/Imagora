# 图片生成主链路

## 主流程

入口页面：`apps/web/app/generate/page.tsx`

核心链路：

```text
/generate 表单
-> POST /api/generation/quote
-> POST /api/generation/tasks
-> queue 提交任务
-> apps/worker/src/main.ts claim 任务
-> packages/ai-providers 调用图片模型
-> packages/storage 保存图片和缩略图
-> API SSE 推送任务状态（断流时退回详情查询）
-> /history、/images/[imageId] 展示结果
```

## 前端状态边界

生成页同时管理几类状态：

- 表单草稿：prompt、negativePrompt、aspectRatio、quantity、quality、model
- 当前任务：task、images
- 提交中状态：loading、submittingGenerationRef
- 恢复状态：taskId URL、active task id、task snapshot
- 预览状态：selectedPreviewImage

这几类状态不能混用。尤其是 `taskId` 恢复和新提交之间有竞态，改动时必须验证：

- 再次生成时旧成功图片不能盖住新 loading。
- 改提示词后 POST body 必须是新提示词。
- 切页再回生成页时，占位卡片数量必须等于当前任务数量。
- active task snapshot 不能被旧 URL 恢复逻辑清掉。

## 页面更新范围

首页入口是服务端组件；静态介绍内容通过 slots 交给 `HomeExperience`，模型与生成入口由 `HomeGenerator` 管理。每 22～42 毫秒变化的打字动画状态仅保留在 `HomePromptInput`，上层接收完整提示词而非逐字状态。

生成页接入 `GenerationForm`、`GenerationModelSelection`、`GenerationProgress` 与 `GenerationResults`。表单和结果区使用独立组件与稳定回调，任务进度更新不会要求无关表单重新执行。组件存在不代表已经生效；维护时需检查页面入口的实际引用。

## API 创建任务

接口：`POST /api/generation/tasks`

职责：

- 校验登录。
- 按配置校验邮箱是否验证。
- 解析模型和生成参数。
- 计算积分成本。
- 创建 generation task。
- 扣减积分并写积分流水。
- 入队或 inline 触发 worker。

这一步只负责创建任务，不负责长时间等待 provider 完成。

提示词审核采用“短事务取快照 → 事务外审核 → 短事务重新校验并扣费落库”。最终事务再次检查生成开关、重试源任务、参考图可用性、当前模型报价、余额和去重键。审核期间输入或生效规则变化时返回 `409 GENERATION_CHANGED`，不创建任务、不扣费；客户端可使用原请求标识重新提交。重复请求直接返回原任务，无需再次调用审核服务。安全拦截事件先提交，再在事务外返回错误，避免事件随异常回滚。

重试接口 `POST /api/generation/tasks/:taskId/retry` 与创建任务共用生成开关、邮箱验证、当前模型/线路报价、参考图审核、提示词审核和扣费流程，也共用生成限流配额。只能重试本人的 `FAILED` / `BLOCKED` 任务，生成参数来自原任务。

请求体可传 `clientRequestId`（8–120 个字符）。同一源任务与请求标识会映射到稳定的去重键，任务创建和积分扣减在同一写事务内完成；首次返回 201，重复请求返回原任务和 200。省略请求体或传 `{}` 的旧客户端也会去重。需要新的尝试时使用新请求标识，或在子任务失败后重试子任务 ID。队列提交失败后再次发送同一请求可重新提交原待处理任务，不会重复扣费。

## Worker 执行

worker 的稳妥模式是两段式：

1. 短事务 claim：`PENDING -> RUNNING`
2. 锁外执行 provider 和 storage
3. 短事务 finalize：写结果或失败

不要让长时间 provider 调用占住 store 写锁，否则 GET 轮询会卡住。

## Provider 约束

OpenAI-compatible 图片 provider 需要明确请求和响应契约。维护时重点看：

- 请求是否显式要求图片数据格式。
- 响应 parser 是否兼容实际 gateway 返回。
- 失败时是否写入可读 failure code/message。

provider 问题不要先改 UI 文案，先确认出站请求和入站 payload。

## 定向读取与 SSE

- 请求日志与仅需身份的路由共用一次按 token 查询，不再预加载整个 Store；会话缓存只在单次请求内有效。
- 任务列表把用户、状态筛选、排序、分页和总数查询下推到 PostgreSQL；退款只读取当前页任务的数据。详情只读取指定用户的任务及关联图片。
- 每个 API 进程只有一个 SSE 批量轮询，默认间隔 1 秒，查询当前订阅的会话和任务。任务版本未变化时，复用图片和退款快照；任务变化时才重新读取关联数据。
- SSE 仍会重新验证会话过期、撤销、用户状态及任务归属。慢连接只保留最新快照，最后一个订阅关闭后释放缓存、停止轮询。
- JSON 模式按原子文件快照版本缓存内容，同一版本的并发读取共用一次解析；返回值与缓存隔离，其他进程写入后重新加载。
- Prisma 初始化锁每个 Store 实例只成功执行一次；普通定向只读不获取全局写锁。索引迁移为 `20260927090000_targeted_read_indexes`，部署时需要通过正常迁移流程执行。

订单列表和详情只查询当前用户的数据；显式传入 `limit` 时由数据库限量返回。GET 仅关闭当前用户的过期订单，不再触发全库对账、积分过期和任务清理；这些由原有后台维护或管理端对账执行。

worker 与 API 的定时任务维护使用 `createGenerationMaintenanceRunner`：按独立游标轮转超时或缺退款任务、存在过期批次的用户，默认每批 100 个任务和 10 个用户。任务仅加载对应账户、TASK 流水及退款幂等键；积分过期必须加载候选用户的完整账本以保持 FIFO 语义。重复调用共用当前执行，失败候选在回绕后重试。故障保留上限由数据库独立处理，不加载所有故障到内存。新增索引迁移为 `9_scoped_maintenance_indexes`；旧迁移采用数字命名，新增迁移必须排在依赖字段创建之后。

SSE 数据源仍是共享定向轮询，没有引入 PostgreSQL LISTEN/NOTIFY。管理端跨实体汇总、订单对账及兼容的完整 Store 写接口仍保留；上述热点读取和专用任务维护采用定向查询，订单对账中的兼容维护仍保留完整 Store 路径。真实 PostgreSQL 行为由 `tests/prisma-store-postgres.test.mjs` 验证；`infra/scripts/scoped-read-benchmark.mjs` 提供合成数据存储层基线，结果不能当作线上并发容量或端到端 SSE 吞吐量。

## 恢复与轮询

历史页的列表、详情和轮询各自维护请求序号与 AbortController。切换项目先使旧请求失效；响应只有在序号仍匹配时才能写入状态。活动任务按最多 100 个 ID 串行分批查询，整轮完成后再安排下一轮；页面隐藏时取消轮询，回到前台后恢复。API client 会保留外部取消原因，取消后到达的响应体也不能写回页面。

生成页支持：

- `taskId` URL 恢复。
- `sessionStorage` 保存 task snapshot。
- active task id 用于切页回来继续展示生成中任务。

这块是高风险区域。改动后至少跑：

```powershell
node --test --test-name-pattern "generate page" tests\web-routes.test.mjs
```

涉及 worker 或 API 锁时，还要跑：

```powershell
node --test tests\api-flow.test.mjs
```
