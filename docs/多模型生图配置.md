# 多 API、多模型生图配置

用户通过按钮切换主线路或备用 API，再从下拉框选择该 API 支持的模型。服务端负责把模型 ID 映射到准确的上游模型名、请求参数、API 地址和密钥；积分也按选中的模型报价。

## 自动识别目录

API 启动时同步各启用线路的 `GET /models`，之后每 10 分钟刷新。默认主线路取现有 GPT 模型的首个启用绑定；可通过 `IMAGE_MODEL_DISCOVERY_CHANNEL` 明确指定通道名。首页和工作台默认显示主线路返回的生图型号；切换备用 API 后，只显示该备用 API 自己的型号，包含备用独有型号。模型下拉框直接平铺模型名称，不含分类标题或搜索框。生成表单不再提供风格预设，画面比例位于提示词输入区右下角，生成数量放在主表单。新任务按提示词自由创作（`style=none`），不附加风格或负向预设；画质默认标准，模型不支持标准时使用该模型首个可用画质。历史任务原记录保留，复用时不会重新注入已移除的隐藏预设。线路与型号偏好在浏览器保存，各线路分别记住型号。

优先使用 `supported_endpoint_types` 中的 `image-generation` 能力标记。没有能力元数据时只能按已知命名识别，不能保证任意供应商的模型名称代表兼容的 Images 接口；需要真实生图验收。保留上游名称的大小写、空格和版本，内部 ID 单独生成。配置中的相同上游型号沿用已有 ID、显示名和价格覆盖。比例能力按精确版本独立解析，不继承其他型号的计费模板；显式 `aspectRatios` 仍作为部署限制，与型号能力取交集。

同步超时、HTTP 错误、维护 HTML 或无效 JSON 时保留上次成功目录。独立缓存保存目录及凭据指纹，不保存密钥；API 地址或凭据变化后不会复用旧账户目录。默认缓存为 `data/image-model-catalog.json`；设置 `IMAGORA_STORE_PATH` 时放在该文件旁，也可用 `IMAGE_MODEL_CATALOG_CACHE_PATH` 指定可持久化文件路径。多实例部署应为每个实例使用独立缓存文件。

管理后台提供“从 API 同步模型”，对应管理员接口 `GET /api/admin/generation/models` 和 `POST /api/admin/generation/models/refresh`，手动刷新保留审计记录。用户端的“刷新模型列表”只重新读取服务端目录。

`IMAGE_MODEL_DISCOVERY=false` 可保留原静态模式。Mock 不访问供应商目录；测试环境只有显式 `IMAGE_MODEL_DISCOVERY=true` 才启用同步。主线路尚未成功取得目录时使用原静态配置兜底；备用线路在自动发现模式下没有成功缓存时显示空列表及错误提示，不能借用主目录。静态模式按所选线路的显式模型绑定返回列表。

## 两层配置

- `IMAGE_CHANNELS` 管理连接：`name`、`baseUrl`、`apiKeyEnv` 或 `apiKey`、`priority`、`enabled`。优先级数值越小越先尝试。
- `IMAGE_MODELS` 管理模型：`id`、`label`、`upstreamModel`、`apiFormat`、`channels`、积分和成本。每个自定义模型必须显式绑定通道。
- 一个通道可供多个模型使用；一个模型也可绑定多个同模型通道。备用通道不会跨到另一种模型。
- `IMAGE_MODEL_DEFAULT` 只决定未选择模型时的默认项，不会覆盖用户明确选择的模型。
- 模型 ID 应保持稳定，例如 `openai:gpt-image-2`、`xai:grok-imagine-image`。`label` 是用户看到的名称，`upstreamModel` 必须填写上游实际接受的名称，三者不要混用。
- `openai` 在这里表示兼容 Images API 的传输适配器，并不表示把所有模型变成 OpenAI 模型。

## 配置示例

以下内容供手动填写根目录 `.env`，不会自动修改已有配置。域名和密钥均为占位内容，价格仅用于演示，必须按自己的收费及真实成本调整。

```dotenv
IMAGE_PROVIDER_DEFAULT=openai
IMAGE_MODEL_DEFAULT=openai:gpt-image-2

GPT_IMAGE_API_KEY=在本机填写GPT通道密钥
GROK_IMAGE_API_KEY=在本机填写Grok通道密钥

IMAGE_CHANNELS='[
  {"name":"gpt-main","baseUrl":"https://gpt-gateway.example/v1","apiKeyEnv":"GPT_IMAGE_API_KEY","priority":0},
  {"name":"grok-main","baseUrl":"https://grok-gateway.example/v1","apiKeyEnv":"GROK_IMAGE_API_KEY","priority":1}
]'

IMAGE_MODELS='[
  {
    "id":"openai:gpt-image-2",
    "label":"GPT Image 2",
    "upstreamModel":"gpt-image-2",
    "apiFormat":"gpt-image",
    "channels":["gpt-main"],
    "creditsPerImage":7,
    "costCentsPerImage":4
  },
  {
    "id":"xai:grok-imagine-image",
    "label":"Grok Imagine",
    "upstreamModel":"grok-imagine-image",
    "apiFormat":"grok-image",
    "channels":["grok-main"],
    "creditsPerImage":3,
    "costCentsPerImage":2
  },
  {
    "id":"xai:grok-imagine-image-2.0",
    "label":"Grok Imagine 2.0",
    "upstreamModel":"grok-imagine-image-2.0",
    "apiFormat":"grok-image",
    "channels":["grok-main"],
    "creditsPerImage":5,
    "costCentsPerImage":3
  }
]'
```

只有供应商确实提供对应模型、密钥有权限，并且支持所选请求格式时，才添加该模型。示例中的模型名不是对任意网关可用性的保证；`/models` 返回模型也不等于支持 `/images/generations`。自动发现开启后，目录提供可选型号，IMAGE_MODELS 提供覆盖配置；目录中的能力描述仍不等于已完成真实生图验收。

`baseUrl` 填 API 根地址，例如以 `/v1` 结尾；不要填写完整 `/images/generations`。系统会自动拼接该路径。`apiKeyEnv` 是环境变量名称，不是密钥内容；也可继续使用旧的 `apiKey` 字段，但两者不能同时填写。真实凭据只保存在服务端环境变量中，不要提交到 Git。

## 请求格式与能力

| `apiFormat` | 请求参数 | 默认画质选项 |
|---|---|---|
| `gpt-image` | `model/prompt/n/size/quality/response_format/output_format`，保持原有 GPT 生图协议 | 草稿、标准、高质 |
| `grok-image` | `model/prompt/n/aspect_ratio/response_format`，不发送 GPT 专有的画质与输出格式参数 | 标准 |
| `openai-images` | 最小兼容参数 `model/prompt/n/size/response_format` | 标准 |

以上均调用 `POST /images/generations` 并请求 `b64_json`，也兼容项目原有的图片 URL 响应处理。仅提供聊天、Responses、Gemini 原生或异步任务协议的服务不能只换地址接入，仍需新增对应适配器。参考图编辑仍未接入，不会把图生图伪装成文本生图。

Grok 的比例、Base64 和 Images 端点已按 [xAI 官方生图文档](https://docs.x.ai/developers/model-capabilities/images/generation) 核对。当前 `grok-image` 适配器只开放“标准”选项，不发送 `quality` 或 `resolution`，采用上游默认值；这不是说 Grok 2.0 本身没有其他质量能力。第三方网关仍需单独验收。

模型可增加 `qualities`、`aspectRatios` 和 `maxQuantity` 缩小能力范围；绑定通道也可增加 `aspectRatios` 单独限制该线路。未声明比例时从上游目录或已核对的型号能力解析，不再默认全开。例如 `"qualities":["standard"], "aspectRatios":["1:1","16:9"], "maxQuantity":2`。请求格式不支持的画质不能通过配置强行开启。正向提示词继续保持全局 7000 字符上限。

首页和工作台通过 `GET /api/generation/models?channel=<通道名>` 获取所选 API 的独立目录。报价和创建任务使用相同的 `channel`；通道不存在、已停用或型号不属于该通道时拒绝请求，不扣积分。用户切换不会修改全站默认通道。切换模型时按其能力选择画质，并同步调整不支持的比例和张数；工作台重新报价。停用模型或没有启用通道的模型不出现在列表中；历史链接指定的不可用模型会提示重新选择，而不会默默换成 GPT。

## 计费和同模型备用通道

`creditsPerImage` 是标准方图的基础积分。普通型号的最终积分为 `ceil(基础积分 × 画质系数 × 尺寸系数 × 张数)`。GPT Image 4K 型号在这个最终整数结果上再乘 2，例如标准方图单张 7 → 14 积分；草稿方图单张 6 → 12 积分，避免先翻倍再取整造成差异。供应商成本不随这个积分倍数自动增加。`gpt-image` 默认沿用原系数：草稿 0.75、标准 1、高质 1.7；非方图尺寸系数 1.22。静态配置中其他格式默认系数均为 1。自动发现的 Grok 型号继承现有 Grok 计费配置（当前基础 3 积分），Banana 和其他新型号继承普通 GPT 的原计费基准（当前基础 7 积分，仅开放标准画质）。已有明确配置的型号保持各自价格；可用 `qualityMultiplier` / `sizeMultiplier` 显式覆盖。

`costCentsPerImage` 为基础供应商成本，单位是分；它不会发送到前端。不同供应商成本不同时，可以在绑定处覆盖，而不能给全部模型沿用同一通道价格：

```json
{
  "channels": [
    "gpt-main",
    {"name":"gpt-backup","upstreamModel":"供应商实际的同模型别名","costCentsPerImage":6}
  ]
}
```

`gpt-backup` 必须先在 `IMAGE_CHANNELS` 中配置。显式模型绑定优先采用绑定的 `upstreamModel`，未指定时使用模型自身的上游名；不会使用旧的通道级模型名覆盖用户选中的模型。不要把不同模型当作别名绑定。失败退款、按张切换和现有熔断策略继续保留。超时后的切换默认仍关闭，避免上游已经生成但重发导致重复收费。选择主线路时保留这些同型号故障切换规则；用户显式选择备用 API 时，任务仅使用该 API，失败不会自动切回主线路或其他备用。

## 画面比例、4K 请求与排队任务

首页与工作台共用 12 种预设比例：1:1、2:3、3:2、3:4、4:3、4:5、5:4、9:16、16:9、1:2、2:1、21:9。以下能力于 2026-09-23 核对，只描述这 12 种预设中的交集，不代表模型的完整比例集合。

| 型号 | 可选范围（未额外限制时） | 依据 |
| --- | --- | --- |
| GPT Image 2、gpt-image-2-2026-04-21 | 全部 12 种 | [OpenAI 旧型号设置](https://developers.openai.com/api/docs/guides/image-generation#earlier-gpt-image-models) |
| GPT Image 1、1 Mini、1.5 | 1:1、2:3、3:2 | 同上，仅三种原生尺寸 |
| Nano Banana 2、2 Lite、Pro 及对应 Gemini 型号 | 10 种，不含 1:2、2:1 | [Google 生图文档](https://ai.google.dev/gemini-api/docs/image-generation#aspect_ratios_and_image_size) |
| Grok Imagine Image、2.0、Pro（Quality 别名） | 10 种，不含 4:5、5:4 | [xAI 比例表](https://docs.x.ai/developers/model-capabilities/images/generation#aspect-ratio) |
| gpt-image-2-4k 等第三方或未知版本 | 仅采用该线路声明或明确配置的比例；无依据时全部禁用 | 不能从名称推断，也不能继承普通 GPT 的范围 |

目录解析优先采用该线路条目的 `supported_aspect_ratios`（兼容 `aspect_ratios`），没有元数据时查精确型号表，再回落到该型号/通道的明确配置。有效集合始终受模型及通道显式限制约束。空元数据列表表示没有可用预设，不会回退为全开；格式错误保留上一份成功目录。同型号在不同线路可以有不同范围，故障切换会跳过不支持当前比例的线路。能力来源通过 `aspectRatioSource` 返回，后台模型表可查看。

旧部署若在 `.env` 的 `IMAGE_MODELS` 中显式保留五种比例，它们仍会限制对应型号；需由管理员移除旧限制，或按线路缩小列表。不能通过修改前端绕过配置。

Grok 使用 `aspect_ratio`；其他格式发送所选比例对应的 `size`。3:4 = 960×1280、4:3 = 1280×960、9:16 = 864×1536、16:9 = 1536×864，不再用三档尺寸冒充其他比例。所有普通预设均为 16 像素倍数，并满足 GPT Image 2 的 3:1、655360～8294400 像素及最大边 3840 限制。返回图片的实际尺寸仍以图片本身为准。第三方 4K 型号现有请求长边为 4096，仅在该线路能力经过确认后使用；这不属于 OpenAI 官方尺寸约定。

可用下列脚本做线路验收。默认只预览参数；加 `--execute` 会产生真实上游生图费用，每个比例只请求一次，禁用重试和备用切换，不创建业务任务或扣业务积分。结果保存在 `.tmp/image-ratio-audit/`，根据解码图片的宽高检查比例（容许 2% 的像素对齐误差）；4K 型号还检查长边至少 4096 像素。请求异常记为未确认并停止后续探测，不能判成模型不支持。报告不会自动扩大生产能力列表。

`node --env-file=.env infra/scripts/verify-image-model-ratios.mjs --channel=<线路> --model=<目录中的型号或ID>`

可使用 `--ratios=1:1,16:9` 缩小验收范围。

“草稿／标准／精细”是画质选项，分辨率由型号决定。GPT Image 4K 请求按比例发送长边 4096 的尺寸：方形 4096×4096、3:4 为 3072×4096、4:3 为 4096×3072、9:16 为 2304×4096、16:9 为 4096×2304。最终交付尺寸从图片本身读取；4K 型号返回长边不足 4096 时任务失败并返还积分，不能用请求尺寸冒充真实尺寸。网关是否接受各尺寸仍以实际调用为准。

任务创建时保存不含密钥的模型、价格及候选线路快照，Worker 根据此快照执行与结算；密钥仍从运行环境读取。刷新目录不会修改排队任务，备用只能切换到快照中的同型号通道。旧任务没有快照时仍按原配置处理。快照不通过普通用户的任务接口返回，只公开通道标识 `channel`，用于任务恢复和历史复用；首页、登录跳转、草稿及图片再创作也保留所选线路。

PostgreSQL 增加可空 `generation_tasks.model_snapshot` JSONB 字段，使用随代码提供的增量迁移；JSON 存储直接兼容。部署 PostgreSQL 版本前需要按正常发布流程执行迁移，不能 reset 数据库。

## 校验与生效

在项目根目录执行静态配置校验，只输出公开模型列表，不发送生图请求（自动同步的当前目录请查看运行中的 API）：

```bash
node --env-file=.env --input-type=module -e "import { getImageModelCatalog } from './packages/ai-providers/dist/index.js'; console.log(JSON.stringify(getImageModelCatalog(), null, 2))"
```

首次更新代码后先执行 `npm run build:packages`。校验通过后，停止旧 API 和 Worker，再分别执行 `npm run dev:api`、`npm run dev:worker`；前端执行 `npm run dev:web`。API 与 Worker 必须加载同一份配置，只刷新页面不能加载服务端的新环境变量。

可通过 `GET http://127.0.0.1:4100/api/generation/models` 检查生效目录。最后再自行选择模型进行真实生图验收，该步骤可能产生供应商费用。

静态模式下，未配置 `IMAGE_MODELS` 时保持旧单模型模式，配置为 `[]` 表示没有可用真实模型；自动发现模式下，`IMAGE_MODELS` 是覆盖配置，实际可选型号来自用户当前所选线路成功同步的目录。`IMAGE_CHANNELS` 仍优先于 `OPENAI_BASE_URL` / `OPENAI_API_KEY`。不要在仍有排队任务时删除其模型配置，避免旧任务因模型停用而失败退款。
